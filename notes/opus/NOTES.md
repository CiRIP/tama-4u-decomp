# Tamagotchi 4U+ firmware (FW_4UPlusJP.bin): understanding notes (opus annotator)

Confidence: **H** = verified in code / several independent clues, **M** = consistent reading
with some inference, **L** = guess. Function names are the repository's `func_XXXXXXX`.
The register inventory is in `peripherals.md`; proposed names in `symbols.tsv`.

## 1. Hardware (see peripherals.md)

* CPU S1C33E07-compatible (all registers used exist in the E07 map at the documented
  addresses) (H). MCLK = 30 MHz from OSC3 without PLL: the ms timers compute
  `t * 30000 >> 12` counts at MCLK/4096, UART reload 0xC3 = 9600 bd (H).
  Low-power mode: OSC1 32 kHz, OSC3 stopped (sys_sleep_osc1) (H).
* External bus: 8 MB bottom-boot NOR flash (8 x 8 KB + 127 x 64 KB sectors, table
  flash_sector_offsets, AMD command set, 16-bit) mirrored at 0x2000000; LCD controller at
  0x600000 (command) / 0x600001 (data) (H). External RAM: .data/.bss at 0x84000..0x845B8
  (H); internal RAM 0..0x5000 (code 0..0xD08, variables, stack top 0x5000) (H).
* LCD: 128x128 TFT, two controller variants selected by the P07 strap at init
  (lcd_init): ST7735(S) (lcd_init_st7735) or another controller with packed init (H).
  Backlight = PWM on TM2 (P12) (H).
* Buttons A/B/C on P00/P01/P02, port-input interrupts 0..2 (H). P06 input = DEBUG strap
  (H): comm_main_menu shows the debug communication menu (extra entries "╬デバックセット"
  and "アイテムSEND") when P06 reads low; sys_sample_debug_strap counts consecutive low samples in
  sys_debug_strap_count (saturating at 8) and main checks sys_debug_strap_count == 8.
* Sound: 4 square-wave channels = T16 ch.0..3 PWM outputs TM0..TM3 on P10..P13, sequenced
  by the T16 ch.4 interrupt (snd_sequencer_tick) (H). Note: TM2/P12 is also the backlight PWM;
  the sound code only seems to use channels 0/1 for key clicks (M).
* NFC: NXP PN512 (or compatible) front-end on serial Ch.1 (P04 SIN1 / P05 SOUT1) in its
  UART host-interface mode, IRQ on P94 (port input 12) (H: register addresses/values match
  the PN512 map exactly: CommandReg 0x01, ComIEn/DivIEn, ComIrq/DivIrq 0x04/0x05, ErrorReg
  0x06, Status2 0x08, FIFOData 0x09, FIFOLevel 0x0A, Control 0x0C, BitFraming 0x0D,
  Mode 0x11, TxMode/RxMode 0x12/0x13, TxControl 0x14, TxAuto 0x15, RxThreshold 0x18,
  Demod 0x19, SerialSpeed 0x1F, RFCfg 0x26, GsNOn 0x27, CWGsP 0x28, ModGsP 0x29, TMode..
  TReload 0x2A..0x2D, VersionReg read 0x37; "WrNFCIDtoFIFO" (Control bit 5) to fetch the
  10-byte NFCID; DivIEn RfOn/RfOff interrupts which the MFRC522 doesn't have).
  P13/P14 GPIO pulses around power-up/down of the front-end (meaning L).
* IR: the same P04/P05 pins are switched to GPIO for an infrared link with another toy
  (P05 = IR LED, carrier bursts generated by a routine copied into RAM; P04 = receiver;
  P03 = receiver power?). Pulse-distance code: start burst 0x170 carrier cycles, per bit
  a 0x12-cycle mark and a 0x64 (1) / 0x36 (0) tick space, LSB first, 20-byte packets with a
  checksum in byte 0x13; stop mark 0x2E (ir_send_packet) (M: pins inferred from usage; the
  data-link timing is H). The IR code is DEAD in this firmware (M-H): all its entry
  points (ir_session via the menu entry ir_menu_hidden_session placed after the end of the
  communication menu tables comm_main_menu_items/D_2538190 (count 4/6), the point-gift menu
  ir_menu_point_gift which nothing references, ir_test_entry, ir_session_receive_only) are unreachable.
  Probably inherited from earlier IR models.
* A/D: battery voltage, threshold 0x2E3 = low battery (H).
* RTC: on-chip RTC for the clock; game keeps its own day/month (H).
* Unused on-chip blocks: watchdog, DMA, LCDC (except IRAM select), I2S, USB, SPI (only
  enable bit toggled by a vestigial SPI-flash driver with empty transfer stubs) (H).

## 2. Boot and system structure

* Vector table 0x2400000 (108 entries); reset -> sys_reset (asm): clocks, wait for
  OSC3 (`slp`), clear IRAM 0..0x5000, SP = 0x5000, bus (sys_bus_setup), GPIO
  (sys_gpio_init), init chain sys_init (runtime, ITC, timers, IRAM code copy, .data
  copy, .bss clear, A/D), nfc_session_clear (clear NFC session), main sys_main (H).
  Interrupt handlers are listed in peripherals.md (H).
* Idle: sys_idle_tick = `halt` then sys_idle_housekeeping (P06 sampling, backlight PWM update,
  ui_call_icon_sync housekeeping) (H). Everything is driven from main loops that call the idle
  routine; there is no RTOS (H).
* Timing: RTC interrupt (rtc_isr, asm, 1 Hz) = the game tick (needs, ages, auto-off
  countdowns ui_timeout/D_0001425...) (M: big handler not fully read). T16 ch.3 = ms timeout
  / NFC 100 ms tick (nfc_ticks) (H). T16 ch.5 = ms delay and IR bit clock (H).
* Interrupts are masked with sys_irq_disable (psrclr IE) / re-enabled with sys_irq_enable
  (psrset IE) around flash programming (H).
* Button events: the port interrupts count presses in btn_a_presses (A), btn_b_presses (B),
  btn_c_presses (C); UI loops poll and clear these (H). ui_timeout = UI inactivity countdown
  (set to 10/30 by menus, decremented by the 1 Hz tick; 0 = time out) (M).

## 4. NFC stack (bottom-up)

### 4.1 PN512 UART driver (asm, asm/nfc/nfc_link.s, lib/nfc_hw/nfc_hw.s, lib/nfc_hw/nfc_hw.s)

* Host protocol (PN512 UART mode): to write register R send `R` then the value; to read
  send `0x80|R`, the chip answers the value. All higher layers build "command scripts" in
  nfc_cmd_buf of (reg, value) pairs and send them with nfc_uart_send, then collect the
  answers (one per pair) with nfc_uart_recv (H).
* nfc_init(ctx): front-end power-on/probe: P04/P05 to SIN1/SOUT1, IRQ pin P94 = port
  input 12 (low active), UART 9600 8N1, wake-up loop (CommandReg = 0x22, read back until
  `(CommandReg & 0x2F) == 0x20` = idle, receiver off), flush FIFO, ControlReg =
  WrNFCIDtoFIFO, read the 10-byte NFCID into nfc_id3 and overwrite bytes 0,1,8,9 with
  F0 40 .. F0 40 (marks this NFCID3 as "a Tamagotchi"), DivIEn = 0x82 (IRQ push-pull +
  RfOn interrupt), clear IRQs, RxThreshold 0x55, RFCfg 0x59, GsNOn 0xF4, TxAuto 0x40,
  TxControl 0x80, CommandReg = 0x37 (soft power-down, receiver off) -> the chip sleeps
  until an RF field appears (P94 interrupt sets nfc_field_irq = 1). Returns 0 / -15 (H).
* nfc_link_open(cfg): open a session: tx/rx ring buffers (nfc_tx_fifo, nfc_rx_fifo, 256 bytes
  each in nfc_tx_fifo_buf/D_00044E8), wake (CommandReg 0x27), check the chip answers (write reg
  0 = 0x55, expect echo), enable UART tx/rx interrupts, set DivIEn 0x81 (RfOff irq),
  clear IRQs, RxThreshold 0x84, RFCfg 0x48, GsNOn 0x88, TxAuto 0, SerialSpeedReg = 0x3A
  (460.8 kbaud), switch the CPU UART to reload 3 (~468.75 kbaud), verify by reading
  SerialSpeedReg, start the 100 ms tick (nfc_tick_start, nfc_ticks). nfc_link_open_921k (unused)
  is the 921.6 kbaud variant (SerialSpeed 0x1C, reload 1) (H).
* nfc_link_close: close: UART interrupts off, 100 ms tick off, NFC IRQ off, CommandReg =
  0x2F (receiver off + SoftReset), CPU UART back to 9600 bd, wait until the chip is idle,
  then the same field-detect configuration as nfc_init (DivIEn 0x82 = RfOn irq,
  RxThreshold 0x55, RFCfg 0x59, GsNOn 0xF4, TxAuto 0x40, CommandReg 0x37 = soft
  power-down) (H).
* nfc_rearm_field_detect (via nfc_sleep_until_field(k)): re-arm the "field detect" sleep, with RfOn (k = 0)
  or RfOff (k = 1) interrupt enabled (nfc_wake_on_field_off) (H).
* nfc_uart_send(buf, n): queue n bytes and start the interrupt-driven transmission (waits
  for the previous transfer); nfc_uart_recv(buf, n, &status): read n bytes from the rx
  ring with a software timeout (99999 polls); status gets the UART error bits (0x1C) or
  0x80 on timeout (H).
* Interrupts: tx empty nfc_uart_tx_isr (send next byte, also drains rx), rx full
  nfc_uart_rx_isr, rx error nfc_uart_err_isr (reads Ch.0 STATUS 0x300B02: probable bug), NFC IRQ
  pin nfc_irq_isr (nfc_field_irq = 1), 100 ms tick nfc_tick_isr (nfc_ticks++, calls
  nfc_request_abort = set the abort flag nfc_abort when nfc_cancel_request == 1) (H).

### 4.2 RF technologies / NFC-DEP (U_252D..., U_2533..., U_2534..., F70d)

Frames are written to the FIFO as `len, cmd, data...` (len includes itself, PN512
"NFCIP-1 start byte" handling) and sent with BitFramingReg = 0x80 (StartSend) while the
front-end runs the Transceive command. Received frames are read by polling FIFOLevel
(0x8A), Status2 (0x88), ErrorReg (0x86): ErrorReg bit 6 (TempErr) -> return 3
(overheat/RF problem), CRC/parity/protocol errors -> ignore frame.

* Passive initiator 106 kbit/s (NFC-A): nfc_setup_passive_initiator configures (Control.Initiator,
  TxMode/RxMode 0, TxControl 0x83 = RF on, Mode 0x3B), nfc_poll_type_a polls: REQA (0x26, 7
  bits), ATQA, anticollision/select cascade 1/2 (0x93/0x95 20), returns the ATQA (H).
* NFC-DEP initiator: nfc_send_atr_req(v): ATR_REQ = D4 00 NFCID3i(10) DID 0 BS 0 BR 0 PP
  (0x32: LR 254 bytes + general bytes / 0x02) + general bytes 46 66 6D (LLCP magic) +
  TLVs VERSION 01 01 11 (1.1) or 10, WKS 03 02 00 13 (SAPs 0, 1, 4 = SNEP) or 00 01,
  LTO 04 01 96 (1.5 s) (H).
* NFC-DEP target: nfc_send_atr_res: ATR_RES = D5 01 NFCID3t ... TO 0x0E + same general
  bytes (H). nfc_send_sensf_res: NFC-F SENSF_RES 01 + NFCID2 01 FE + NFCID[0..5] + PMm
  C0..C7 (answer to an NFC-F/FeliCa poll "FF FF ..": the toy can be found by a phone
  polling NFC-F 212/424) (H).
* Active mode 424 kbit/s (TxMode/RxMode 0xA1): nfc_setup_active_initiator (initiator side config) and
  nfc_detect_initiator (target side: waits for ATR_REQ D4 00, accepts only NFCID3 starting with
  F0 40 = another Tamagotchi, answers ATR_RES) -> tama-to-tama link (M on "active mode":
  inferred from TxMode framing bits).
* DEP PDUs: D4 06 PFB (DEP_REQ) / D5 07 PFB (DEP_RES), PFB = PNI 0..3 for information
  PDUs, 0x80 = supervisory ATN (nfc_send_dep_res_atn), 0x10 MI bit = chaining (nfc_snep_server
  acknowledges chained frames with an ACK PDU 0x40|PNI) (H).

### 4.3 LLCP + SNEP (F70d nfc_snep_server / nfc_snep_client, U_2533..U_2534)

LLCP header byte0 = DSAP<<2 | PTYPE>>2, byte1 = (PTYPE&3)<<6 | SSAP, I/RR PDUs add an
N(S)/N(R) byte. PDUs built here (all H):
* SYMM 00 00 (nfc_llcp_send_symm_req as initiator, nfc_llcp_send_symm_res as target);
* CONNECT 11 20 (DSAP 4 = SNEP, SSAP 0x20) (nfc_llcp_send_connect);
* CC 81 84 + MIUX TLV 02 02 00 00 (nfc_llcp_send_cc);
* DM 81 C1 02 ("no service", reply to a CONNECT to SDP SAP 1) (nfc_llcp_send_dm_sdp),
  DM 81 C4 00 (reply to DISC) (nfc_llcp_send_dm);
* DISC 11 60 (nfc_llcp_send_disc), DISC from SAP 4 81 44 (nfc_llcp_send_disc_server);
* RR 13 60 nr / 83 44 nr (nfc_llcp_send_rr);
* I-PDUs with SNEP data: nfc_snep_send_put (client: send next fragment of a PUT),
  nfc_snep_send_response (server: SNEP response 10 80 = Continue / 10 81 = Success).
* nfc_snep_server = SNEP **server** (toy receives): accepts CONNECT to SAP 4 from SAP 0x20 or
  to SAP 1 from 0x21 (answers CC), first I-PDU: SNEP header 10 02 (PUT) + 4-byte length
  (big endian) -> if length > 0x7A send Continue and collect fragments, else wait for
  completion; sends Success (0x81) at the end; payload handled by nfc_snep_store_fragment (H).
* nfc_snep_store_fragment = SNEP PUT payload sink: parses the NDEF record header (SR flag 0x10,
  type length, 1- or 4-byte payload length) of the first fragment, stores the record
  PAYLOAD either into a RAM buffer, or (flag) programs it straight into NOR flash at
  the destination address halfword by halfword (IRAM func_0000B52), keeping an odd byte
  in nfc_snep_odd_byte between fragments (H).
* nfc_snep_client = SNEP **client** (toy sends): CONNECT to SAP 4, on CC send the PUT in
  I-PDU fragments (nfc_snep_send_put), handle RR / I (Continue/Success responses), DISC (H).
* The toy is the NFC-DEP initiator in this path (polls with REQA, sends ATR_REQ), but it
  also handles being a target (ATR_REQ D4 00 / DEP_REQ D4 06 / SENSF poll from the
  phone) (H).

### 4.4 Reader mode (cards/accessories) (lib/nfc/nfc_reader.. U_2533..., F51 spot_reader)

nfc_poll_tag/252D882/252D9C0/252DAE4/252DBB6 open the front-end and poll a card
(nfc_activate_type_a, nfc_poll_felica) whose type code is 0x0004/0x0002 (MIFARE Classic?),
0x0044/0x0810/0x0812/0x0816 (Ultralight/NTAG-like?) or 0x0EEF (an ISO-DEP/APDU card:
status word 0x9000 checked, keys/AIDs set with card_set_params); read (nfc_mifare_write /
2532650 / 253284A) or write (nfc_mifare_read / 2531864 / 2531BD8, in 0x7FFE chunks).
Only user: spot_reader (a "touch an IC card/accessory" screen): reads a 0x30/0x3C-byte
header, checks its CRC (spot_check_sum), and for payloads up to 0xF000 bytes writes them
to flash 0x2050000 (M: card types are guesses from the codes).

### 4.5 Session layer: "TAMAGO" packets (F69, F70b, F67, F66)

* nfc_session (0x24 bytes) = session state: x000_b busy flag, x001 front-end status
  (1 ok, 2 failed), x002 role (1 = initiator/sender, 2 = receiver/waiting side),
  x003 session type (1..10, see below), x004 peer kind (0xF040 = another Tamagotchi,
  0xF0F0 = phone/app?, 0xF0EF = not detected), x006 detected peer kind, x010 pointer to
  received friend data, x014 extra string (H for fields used, M for meanings).
* Entry from the UI: nfc_menu_session(menu item a): sets type/role (1: type 2, 2: type 3,
  3: type 5, 4: type 7, 5: type 6, 6: type 8 role 2, 7: type 8 role 1), then the
  initiator path nfc_session_initiator or the waiting path nfc_session_target (H).
* Communication menu (comm_main_menu, F7) -> session types (H unless noted):
  - "あいさツーしん" (greeting) = profile exchange: type 2 (comm_greeting_session);
  - "たまごっち4U" submenu: "ツーしんゲーム" connection games (hide-and-seek, cooking,
    castle treasure, model coordinate) = type 3 (falls back to 4), "アイテムこうかん"
    give an item = type 5 (comm_gift_item = item file), "きねんしゃしん" photo = type 7,
    "プロポーズ" marriage = type 8 with role by choice (M for proposal mapping);
  - "4Uアプリ" (phone app) = type 8 role 2: the app pushes data (SNEP), peer kind 0xF0F0;
  - "タッチスポット" (Touch Spot kiosk) = NFC READER mode (spot_touch_menu_entry ->
    spot_reader): reads an ISO-DEP card/tag with APDUs (status 0x9000), up to 0xF000
    bytes into flash 0x2050000;
  - debug only (P06 low): "デバックセット" (test_debug_set_character), "アイテムSEND" = type 8 role 1.
  - type 0 (automatic, nfc_idle_session): when an RF field wakes the toy on the main screen
    (nfc_idle_touch), the peer decides the type (received +0x4C).
* nfc_find_peer_target / nfc_find_peer_initiator detect the peer (nfc_detect_initiator as target, nfc_detect_target as
  initiator), nfc_send sends a buffer (tama: nfc_dep_send, else SNEP client
  nfc_snep_client, with retries), nfc_receive receives (tama: nfc_dep_receive, else SNEP
  server nfc_snep_server), nfc_result = last result (H).
* Exchange (comm_exchange_initiator for role 1, comm_exchange_target for role 2): up to three rounds, each
  "build a TAMAGO packet in the flash tx area, send it, receive the peer's packet into
  the flash rx area, validate it (comm_validate_record)": round 1 at +0 (type 1: 0x2000-byte
  test pattern 0x55AA/0xAA55; type 2: profile packet in RAM 0xA0/0xA1), round 2 at
  +0x800 (session data, packet codes 0x20..0x29 / 0x10..0x13 = (type, role) from
  comm_phase2_code), round 3 at +0x400 (final ack 0x90/0x91) (H).
* TAMAGO packet header (0x100 bytes, comm_tx_record = own, comm_rx_record = peer copy): +0x00
  "TAMAGO" magic + name (filled by strcpy of D_256255C), +0x48 u32 total length
  (header + chunks + 2-byte sum), +0x4C session type, +0x4D ?, +0x52 string (D_2562564 /
  D_2562570), +0x5E packet code, +0x5F own id (pet_get_gender), +0x60 16-byte name/ID
  (owner_name), +0x72 character id, +0x74.. character state (age, generation, etc.), +0xD8
  ?, +0xE0..+0xEC offsets of the chunks, +0xF8 flags, +0xFF bit 0 = valid. Chunks after
  the header: {u32 type, u16 version, u16 length} + data, 4-byte aligned: type 1 (name
  string, comm_build_section_poses), 2 (0x54/0x5E bytes of character data, comm_build_section_profile), 3 (a whole
  downloaded TAMAGO file copied from flash, comm_build_section_item), 4 (100-byte record,
  comm_build_section_mail), 5 (string, comm_build_section_proposal), 6 (comm_build_section_images2). Last 2 bytes = 16-bit sum of
  all previous bytes (comm_record_sum) (H for layout, M for the meanings).
* Validation comm_validate_record (returns 0 or 0x4D): magic "TAMAGO", length 0x100..0xF000, byte
  sum, an 8-byte signature at +0x52..+0x59 checked against two 16x8 permutation tables
  (D_25623D8 / D_2562458) indexed by the nibbles of byte +0x55, flag +0xFF bit 0, +0x84
  type (H for the checks, M for "signature").
* Downloaded files (from the app/server) use the same 0x100-byte TAMAGO header but with
  big-endian length (comm_build_section_item byte-swaps +0x48 of the file at comm_gift_item) and a
  UTF-16BE file name at +0x06 ("DL_T4Ud_ごはん.jpg"), ASCII id at +0x34 ("t4u_gh00001_1"),
  category bytes +0x4E/+0x4F/+0x51 (0x81 = item/food?, 0x94 02 = game/app), +0x5A/+0x5B
  = 16-bit content id, and for games a big-endian entry offset at +0xAE..+0xB1 (H).

## 5. Code execution from downloaded payloads (H)

### 5.1 The chain (all steps H, verified in code)

1. Delivery. Phone app ("4Uアプリ", session type 8, role 2): the app pushes TAMAGO
   packets with SNEP PUT over LLCP; nfc_snep_store_fragment programs the NDEF payload straight into
   the flash receive area 0x27D0000 / 0x27D0800 / 0x27D0400 (rounds 1..3). Also possible
   from another toy (type 5 "give an item": the item file travels as chunk type 3) and
   from Touch Spot kiosks (reader mode, block at flash 0x2050000, spot_content_browser).
2. Validation of the packets (comm_validate_record): "TAMAGO" magic, length 0x100..0xF000, 16-bit
   byte sum, 8-byte "signature" at +0x52 checked through the permutation tables
   D_25623D8/D_2562458 selected by byte +0x55, +0xFF bit 0; consistency between rounds
   (comm_check_peer_phase: same peer name +0x60 / id +0x72, packet codes); the attached file must
   have flag 0x10 in its +0xFF (comm_check_item_flag); for type 8 a few item kinds are refused
   (comm_check_app_food). No cryptographic signature: the check is a fixed table lookup that
   anyone with the firmware can reproduce.
3. Storage (comm_outcome_app -> item_receive -> item_store_in_bank): the attached file (packet +
   +0xE6 + 8, comm_record_item) is filed by its category bytes: 0x81/1/1 -> category 0,
   0x81/1/2 -> 1, 0x81/3 -> 2, 0x81/2 -> 3, 0x81/4/1 -> 4 (or specials 15/16), 0x81/4/2
   -> 5, 0x81/7 -> 6, 0x81/6/1 -> 9, 0x81/8 -> 17/18, **0x94/2/1 -> category 7 (games,
   2 x 32 KB at flash 0x2710000)**, **0x94/2/2 -> category 8 (town places, 4 x 32 KB at
   0x2720000)**, 0x94/2/3 -> downloaded CHARACTER (8 x 32 KB at 0x2780000,
   dl_chara_store). Same file already present -> replaced; no free slot -> the user picks one
   to delete (item_bank_discard_browser). Programmed with flash_program_record.
4. Installation and execution: the game center (town_game_corner -> game_menu, entries
   after the two built-in games "おたからザクザク"/"ケーキできるかな") and the town map
   (town_menu, entries 8..13) take `p = item_bank_slot(cat, slot)`, call dl_install_program(p)
   which erases flash sectors 1..k+1 (offset 0x0..) and copies the whole file (size =
   be16(p+0x202) + 0x204) to 0x2000000 (only for +0x4E == 0x94, +0x4F == 2; skipped when
   the same +0x51/+0x5A/+0x5B ids are already installed), then
   `r = ((int (*)(void))(0x2000000 + be32(p + 0xAE)))();`
   i.e. native S1C33 code from the downloaded file runs in place from NOR flash, as a
   normal C function, with full access to RAM, peripherals and the firmware.
5. Return: r = result class (0..5) or a point value -> rewards (points, happiness, weight,
   result animations, play counter pet_game_count); after a downloaded game with the best
   result dl_chara_affection_update(0x2000000) and pet_add_traits(0x20000B8) read the installed
   file's own header (category, trait bytes +0xB8).

### 5.2 The ABI offered to the programs (M)

The firmware has a block of thin wrappers at 0x2400B64..0x2401DA0 (buttons get/set,
random, pet stats get/add, clock, delays/timers, sounds, display objects, animation
frames, picture resource table api_picture_address with 346 pictures, character sprites...).
Several have no caller in the firmware, and the built-in mini-games (0x251C..0x2527) use
them instead of the engine functions directly: very likely the programming interface of
the downloadable games/places (they are linked at 0x2000000 + offset and call these
fixed addresses). The engine functions are separated by `.space` gaps with `ret`
stubs (e.g. 0x2401DD6, 0x2402012...), maybe to keep the entry points stable.

### 5.3 Other "code from data" checks

* Indirect calls/jumps whose target is not a constant (work/icalls.py): all go through
  firmware tables (switch tables, menu tables {text, callback}, animation tables,
  town_places place callbacks, game_menu_tbl game entries, sound callback snd_period_table) except the
  two launchers above (H for the list, M for exhaustiveness).
* sys_apply_patch_list applies a list of {address, mask, value} patches to arbitrary memory
  (byte/halfword/word) but has NO caller (dead, or an API for external code) (H for "no
  caller").
* The interrupt handlers of the IR bit timer run from internal RAM (0xD58, 0xD94) after
  being copied from flash by sys_copy_ram_routines (firmware code, not downloaded) (H).

## 6. Main structure (M)

* main (sys_main, asm): power-on sequence sys_startup_flow (logo, battery, load save or
  factory reset + first set-up), then a loop: events (pet_care_event_dispatch), stage changes
  (evo_stage_change), the 10 icons (ui_main_icon = selected icon, jump table D_253EF48: food,
  care, ..., communication, town ...), idle `halt`, display sleep after the inactivity
  countdowns, RF-field wake-up -> automatic NFC session (nfc_idle_touch).
* RTC 1 Hz interrupt (rtc_isr, asm): clock (rtc_read_clock); per second the screen
  and timeout counters; on minute changes the life simulation (pet_minute_tick), daily
  events (pet_clock_events), jobs/away modes (job_minute_tick, outing_minute_tick...), scheduled
  friend events (friend_event_minute_check); wakes the display with a beep when something happens.
* Saving: save_game after state changes (flash sector 8).
* Test mode (test_mode, asm) entered at power-on with a button held: LCD colour
  fills, buttons, sound, firmware/graphics checksums (test_rom_sum_program/func_251970A),
  battery, NFC probe ("NFC INITIALIZE OK/NG"), flash reset (test_flash_erase_all).
